# Тесты payments_api

Первый пункт выполнен в исходном проекте: **84 теста проходят** на Python 3.13
и SQLite, локально и в Docker. Тесты содержат комментарии и docstring
с объяснением проверяемых рисков.

## Запуск

Из корня проекта в Windows, используя его виртуальное окружение:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-test.txt
.\.venv\Scripts\python.exe -m pytest -q
```

В активированном окружении достаточно `python -m pytest -q`. Файл
`requirements-test.txt` включает зависимости приложения из `requirements.txt`
и инструменты тестирования. В текущем `.venv` они уже установлены.

Для подробного вывода или отдельной группы:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_idempotency.py -v
.\.venv\Scripts\python.exe -m pytest tests/test_webhooks.py -v
.\.venv\Scripts\python.exe -m pytest -m concurrency -v
```

Uvicorn запускать не требуется: HTTPX обращается к ASGI-приложению внутри процесса.
AnyIO запускает асинхронные тесты на asyncio; pytest-asyncio не нужен.

## Изоляция и гонки

Каждый интеграционный тест использует собственный файл SQLite в `tmp_path`.
Настоящие миграции Alembic применяются к этому файлу; затем выполняется настоящий
lifespan приложения с заполнением тарифов. Фабрики сессий подменяются до его запуска,
поэтому тесты не подключаются к рабочей `payments.db`.

В пяти сценариях гонок барьер синхронизирует чтение: оба запроса видят исходное
состояние до записи. HTTP-запросы, SQLAlchemy и операции SQLite остаются настоящими;
`sleep` для имитации конкуренции не используется. Тайм-ауты не дают барьеру зависнуть.

В сценарии посторонней ошибки БД тестовая сессия сначала выполняет настоящий
`flush`, а затем намеренно выбрасывает `IntegrityError` до `commit`. Проверяется,
что обработчик вызывает `rollback`, не сообщает об успехе и не оставляет платёж.
При гонке одинаковых ключей нарушение уникальности возникает в самой SQLite.

## Найденные ошибки и исправления

На исходном коде: **73 passed, 11 failed**. Падения выявили две причины:

1. SQLite возвращает `created_at` без часового пояса. Создание платежа отвечало
   временем с `Z`, а GET и повтор по ключу теряли зону. В `app/schemas.py`
   добавлена нормализация к UTC согласно существующему правилу модели, которая
   записывает время создания в UTC.
2. Два вебхука могли прочитать один исходный статус, оба пройти проверку и оба
   вернуть 200. В `app/main.py` прежний статус проверяется в условии `UPDATE`.
   Второй запрос получает 409, если первый уже применил переход; это также
   защищает от одновременных одинаковых уведомлений и повторного возврата.

После этих двух исправлений: **84 passed**, без `skip` и `xfail`. На этапе тестирования
из существующих файлов приложения изменены только `app/main.py` и `app/schemas.py`; модель таблиц
и миграции сохранены. Новые файлы: `tests/`, `pytest.ini`, `requirements-test.txt`
и эта инструкция.

## Границы проверки

Проверен текущий стек Python 3.13.6, FastAPI, SQLAlchemy и SQLite. Повторный lifespan
проверяет сохранение данных при повторном запуске приложения в одном процессе;
аварийное завершение и перезапуск отдельного процесса здесь не моделируются.
Настоящий банк, подпись вебхука, PostgreSQL, контейнерная сеть, нагрузка множества
процессов и одновременный seed нескольких процессов требуют отдельных проверок.

Запуск тестов в Docker описан в [DOCKER.md](DOCKER.md). Общий README и AI_LOG.md
относятся к следующим пунктам задачи.
